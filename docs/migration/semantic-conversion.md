# Canonical semantic conversion to Semantic STRling and Simply

## Outcome and authority

P15-T02 defines a reusable conversion boundary from validated canonical
Semantic IR into the two semantic authoring destinations already ratified by
the repository: `strling.semantic@1.0.0` text and a direct-operation
`strling.simply-builder@1.0.0` request. The permanent conversion-result
identity is `strling.semantic-conversion@1.0.0`; its versioned contract belongs
under `spec/conversions/semantic/1.0/`.

Conversion starts from canonical Semantic IR. It never translates historical
regex text, target regex, emitted artifacts, formatter syntax evidence, or
binding objects. The existing Semantic STRling grammar/formatter contract,
Simply protocol, Semantic IR contract, normalization, and semantic explanation
model remain authoritative for their respective scopes.

The clean starting and rollback boundary is
`5ad4ff67e3fb7ff517c2aec4c16ca6dc40b91408`. P15-T01's structured explanation
model is complete at that revision. P15-T02 cannot reopen explanation meaning,
change `CompileResult` 1.0, or begin the bounded whyNoMatch work assigned to
P15-T03.

## Versioned conversion result

One closed result records:

-   conversion model, compiler-contract, semantic-specification, and
    destination contract identities;
-   the canonical source-program digest and destination;
-   status `exact`, `partial`, or `unsupported`;
-   optional generated output: UTF-8 Semantic STRling text or a host-neutral
    Simply BuilderRequest JSON value;
-   source-node and capture mappings to generated byte spans or Simply
    step/capture keys;
-   equivalence evidence and the exact normalized alpha-projection method;
-   structured losses, unsupported constructs, required manual decisions, and
    conversion diagnostics;
-   semantic-explanation references by model version, program digest, node
    identity, and evidence class; and
-   optional target/profile annotations copied from an exactly corresponding
    target-aware explanation without influencing conversion semantics.

`exact` is permitted only when reconstructing the generated destination through
its existing canonical frontend produces normalized Semantic IR equal under the
certified alpha projection. The projection alpha-renames node and logical
capture identities and removes sources/origins; it retains case intent, every
node/member value, capture names, ordering, repetition, assertions, and all
other semantic data. Emitted-text similarity is never proof.

`partial` requires usable generated output plus at least one explicit loss or
manual decision and cannot carry a proven-exact claim. `unsupported` carries no
executable output and identifies every blocking construct discovered within
the bounded traversal. No status permits an unrecorded approximation.

## Semantic STRling representable domain

All twelve canonical node kinds and four character-set member kinds have a
ratified textual form. Exact conversion additionally requires every capture to
have a unique name valid under the Semantic STRling 1.0 identifier/reserved-word
rules and every backreference to follow a completed, non-self, non-recursive
capture definition in semantic traversal order.

An unnamed or textually invalid capture may produce deterministic valid text
only as `partial`, with an explicit capture-name substitution and manual
decision. Forward, self, or recursive backreference topology is `unsupported`
for this destination because inserting placeholders or reordering constructs
would silently change matching behavior. All other strings, scalars, set
members, positions, modes, directions, polarities, and options use the existing
canonical Semantic STRling escaping and spelling rules.

Canonical Semantic IR intentionally does not retain authored comments or set
member order. Conversion emits no comments and uses canonical member order.
The result always records the `semantic_ir_only` comment policy; it never reads
raw source text to recover prose. Comment absence is non-semantic metadata and
does not by itself weaken an otherwise exact semantic proof.

The renderer records each generated material node's half-open UTF-8 span and
each capture identifier span. A parse of the generated text must succeed under
the existing source frontend before output can be returned.

## Simply representable domain

Every validated canonical Semantic IR node/member kind maps to one of the
existing direct construction operations. Conversion emits child-before-parent
steps, never `import_node`, `import_program`, `stdlib_helper`, raw regex, target
syntax, or a host-language source file. Stable step and capture keys derive
from canonical traversal ordinals; a deterministic identity namespace derives
from the source semantic digest.

The request preserves case matching, character domains, wildcard line
terminators, repetition modes, positions, lookaround intent, capture names,
and logical references. Compile routing is empty and target-neutral. Replaying
the generated request through the existing Rust Simply decoder/builder and
normalizer must prove alpha-equivalent semantics before status can be `exact`.

## Explanation and target boundary

Conversion issues use stable codes and exact source node/capture identities.
When an exactly corresponding semantic explanation is supplied, issue records
link to its structured node/fact evidence rather than generating narrative
prose. A target-aware explanation may contribute immutable target profile,
status, decision ordinal, capability, constraint, or rewrite references. These
annotations do not change destination output or turn target portability into
semantic representability.

Missing explanation evidence does not invent a fact. A mismatched explanation
program digest, model version, or node reference rejects the operation rather
than degrading silently.

## Resource, architecture, and public boundary

The conversion traversal is pure, deterministic, bounded by the existing
Semantic IR/frontend limits, and independent of filesystems, networks,
processes, clocks, runtime engines, bindings, packages, the LSP, and product UI.
It may call only canonical validation/normalization, the two destination
reconstruction frontends, canonical hashing, and exact explanation
correspondence. It cannot analyze raw regex, plan targets, lower, emit, execute,
or create a second semantic model.

The intended additive Rust API is one destination enum, closed result/evidence
types, structured errors, and a pure conversion function. Existing compiler,
frontend, Simply, explanation, binding, and protocol APIs remain compatible.
The Rust public snapshot and architecture mapping must record this addition.

## Verification and handoff boundary

Before implementation, CP2 must freeze a closed schema, positive exact/partial/
unsupported fixtures, controlled negatives, representable-domain coverage, and
mutation evidence. CP3 must prove destination reconstruction, alpha equality,
deterministic bytes, provenance maps, explanation correspondence, and no-panic
bounded traversal. CP4 must cover imported regex -> canonical IR -> both
destinations -> reconstruction, applicable real-target execution, public and
architecture contracts, migration differential, and Local/Pull Request/Full
profiles as available.

Task closure records exact/partial/unsupported counts, losses, manual decisions,
round-trip results, target limitations, contract fingerprint, final SHA, and
P15-T03 readiness. Broad CLI/LSP/editor UX, binding code generation, target
emission, comment parsing, and whyNoMatch tracing are explicit non-goals.
